# Design

## Context

動機見 proposal，需求見 `specs/llm-selection/spec.md`。已確認的現況：

- 追蹤結果是 `result.txt`，每列 `frame,id,x,y,w,h,conf,-1,-1,-1`（影格與身分為整數）。檔案**沒有**影像尺寸或幀率；`seqinfo.ini` 只在 MOT17 資料夾有，api 上傳的任意影格資料夾不一定有。
- 這台機器已有 MOT17-09-FRCNN 的真實 Result：`data/results/full-fp16-3/results/MOT17-09-FRCNN.txt`（`data/results/` 被 git 忽略）。實測內容：3,384 列、影格 1–263、49 個不同身分。它是**驗證半段**（重新編號後的 263 張），不是完整的 525 張；題目與報告以這個檔案的實際範圍為準，並記錄它的 sha256。
- GPU 是 RTX 5090（32 GB），目前空閒；沒有安裝 Ollama、vLLM、llama.cpp，Docker 裡也沒有 LLM 執行環境。`eval/latency.py` 已有讀整張 GPU 已用量（MiB）的探針 `read_gpu_memory_mib`，可重用於量 worker 與模型的顯存。
- 專案慣例：套件各自成資料夾（`eval/`、`tracking/`…），測試在 `tests/`，`integration` 與 `gpu` 標記預設不跑；Docker daemon 是 sidecar，先前的端對端測試用具名卷與 tar 串流，不 bind mount 工作目錄路徑。
- 沒有安裝任何 LLM 用戶端套件；Ollama 提供 HTTP API，可以只用標準函式庫呼叫。

## Goals / Non-Goals

**Goals:**

- 用同一套題目、同一組門檻，可重跑地比較 3–4 個候選本機模型，選出可與 worker 共存的預設模型。
- 標準答案與工具互相獨立，避免「同一個 bug 一起通過」。
- 評估只動專屬名稱的資源，結束後清乾淨，只留記錄。
- 沒有候選通過時如實回報，不調整門檻。

**Non-Goals:**

- agent 迴圈、對外命令列、api 端點、映像相依（屬於 `add-tracking-query-agent`）。
- 雲端模型、向量資料庫、微調、vLLM／llama.cpp 的比較。
- 影像內容理解（衣服顏色、動作等）。
- 把評估放進 CI（需要 GPU 與數十 GB 下載）。

## Decisions

### D1：套件配置與資料流

新套件 `llm_eval/`：

- `llm_eval/results.py`：讀 `result.txt` 成列（只給工具用）。
- `llm_eval/tools.py`：五個工具與它們的 JSON schema（給 Ollama 的 `tools` 欄位）及參數驗證。
- `llm_eval/oracle.py`：標準答案程式。**不匯入** `tools.py` 與 `results.py`，自己逐行讀檔；測試用 AST 檢查匯入清單，並檢查雙向都沒有匯入。
- `llm_eval/questions.py`：由 Result 檔與種子產生題目（文字、種類、標準答案、不可回答的類別）；輸出 `questions.json`。
- `llm_eval/ollama.py`：以 `urllib` 呼叫 `/api/chat`、`/api/pull`、`/api/ps`、`/api/show`。
- `llm_eval/score.py`：把一次試驗的原始回應轉成四項指標與標記。
- `llm_eval/docker.py`：專屬容器的建立、拉取、清理與前後清單比對。
- `llm_eval/run.py`：命令列，把以上串起來，寫出每個候選的原始結果與彙總。

資料流：`result.txt` →（`questions.py` + `oracle.py`）→ 題目與標準答案；題目 →（`ollama.py` 對候選模型，工具由 `tools.py` 執行）→ 每次試驗的原始紀錄 →（`score.py`）→ 指標 → `docs/llm-selection.md`。

### D2：五個工具與兩個約定

| 工具 | 參數 | 回傳 |
| --- | --- | --- |
| `count_unique_ids` | `min_frames`（整數，預設 1） | 不同身分數 |
| `track_span` | `track_id` | 第一張與最後一張影格 |
| `people_in_frame` | `frame` | 該影格的人數 |
| `dwell_frames` | `track_id` | 該身分出現的影格數 |
| `ids_in_region` | `x_min,y_min,x_max,y_max`，可選 `frame_start,frame_end` | 在區域內的身分清單 |

- **人數的定義**：`count_unique_ids` 預設 `min_frames=1`，即原始身分數（Tracker 的誤報也會形成短暫的 Track）。題目沒有明確給「至少出現 N 張」時，答案就是原始數；模型被要求在答案註明定義。
- **區域**：框底邊中心點 `(x + w/2, y + h)` 在 `[x_min, x_max] × [y_min, y_max]` 內才算。座標是 Result 檔的像素座標；沒有影像尺寸，所以沒有「左半邊」這種相對說法。
- **停留時間**：只用影格數。結果檔沒有幀率，所以「幾秒」屬於不可回答的類別（缺少結果檔沒有的序列資訊）；回應也可以改用影格數回答並明說單位，兩者都算正確。
- 這是**評估用的最小工具集**；`add-tracking-query-agent` 會在實測選型後再把它正式化，這個 change 不承諾它的最終形狀。

### D3：標準答案的獨立性

`oracle.py` 逐行 `open(...).read().splitlines()`，用最直白的迴圈與 `set`／`dict` 算；不呼叫 `results.py` 或 `tools.py`。獨立性靠三件事保證：

1. AST 測試：`oracle` 的匯入不含 `llm_eval.tools`／`llm_eval.results`，反向亦然。
2. 手算驗證：一個人工建構的小序列（每列都是手寫的數字），三題以上的答案由人手算後寫進測試，oracle 必須完全一致。
3. 交叉測試：在合成序列與真實序列上，工具輸出與 oracle 輸出逐題比較；兩者不同時測試失敗並印出題目，這能抓到「其中一邊有 bug」。（交叉測試的存在不削弱獨立性：兩者仍然各寫各的。）

### D4：題目組成

共約 30 題（固定種子，產生器本身有單元測試保證相同輸入得到相同輸出）：

- 可回答（約 21 題）：每個工具 3–5 題，參數取自真實資料（例如實際存在的身分、實際範圍的影格、有人經過的區域與沒人經過的區域）；真實序列 15 題，合成序列 6 題。
- 不可回答（約 9 題）：五類各至少一題，影像內容 2、需要結果檔沒有的資訊 3（相對區域、秒、影像尺寸）、跨序列 1、預測 2、對應真實人物 1。
- 合成序列：人工建構，涵蓋空檔案、單一身分、身分 A 在第 3–5 張出現、第 10–12 張重現（同一個 id）、某影格 40 個身分；答案一眼可知。每個邊界情況至少一題。

題目檔 `questions.json` 與每題的標準答案由產生器寫到 `data/llm_eval/`（被 git 忽略）；題目的產生程式與合成序列的資料（小，數 KB）進版控。

### D5：呼叫協定與評分

- `POST /api/chat`，`stream=false`，`options: {temperature: 0, seed: 固定值}`，`tools` 帶五個工具的 schema。
- 最多 4 輪：模型回傳 `tool_calls` → 我們執行工具並把結果以 `tool` 角色送回 → 模型再回。最後一輪用 Ollama 的 `format`（JSON schema）要求結構化的最終答案 `{"refused": bool, "category": "...", "value": ..., "unit": "...", "definition": "..."}`。
- 結構化輸出讓評分是客觀的、不靠解析自由文字；代價是可能掩蓋模型在自由文字下的行為，報告的限制段會寫明。
- 工具呼叫格式正確：工具名在集合內，且參數通過型別與必填檢查（不論題目答對與否，都以每一次工具呼叫計）。
- 答案正確：數值型完全相等，清單以集合比較；可回答的題目 `refused` 必須為 false。
- 拒答正確：不可回答的題目 `refused` 為 true 且 `category` 等於該題類別；「秒」的題目另外接受「改用影格數並明說單位」。
- 延遲：每次試驗從送出第一個請求到收到最終答案的牆鐘時間，報告中位數與每題分佈；模型載入的第一次請求另外標示並不計入中位數（先做一次暖機請求）。
- 與工具輸出不一致：最終 `value` 與最後一次對應工具的回傳不同時標記，只記錄不設門檻。

統計以「題數 × 3 次」的所有試驗為分母；另外回報「3 次不一致的題數」。

### D6：門檻與選擇規則

門檻寫在 `llm_eval/thresholds.py` 與文件中，並有測試鎖定數值（0.90、0.90、0.95、16 GiB）：**先於任何評估結果**提交，之後若要改要走使用者決定的流程。

通過者中依序：延遲中位數最低者；若兩者相差在 10% 內，選載入後顯存較小者；報告列出所有通過者。沒有通過者時，報告列每個候選未達標的指標與數值，結論為「沒有候選通過」，不選。

### D7：Ollama 容器與資源邊界

- 容器 `openmot-llm-eval`，具名卷 `openmot-llm-eval-models` 掛在容器內的模型目錄，`--gpus all`，埠 11435 綁 `127.0.0.1`（不用預設 11434，避免與使用者可能存在的實例衝突；可由環境變數覆寫）。
- Ollama 映像的標籤在實作時查證 Docker Hub 後**釘版本**並記錄摘要；現在不預先決定。
- 前後比對：評估前存 `docker ps -a`、`docker volume ls`、`docker images` 三份清單（存在評估輸出目錄），結束後重新取得並 `diff`，只允許出現 `openmot-llm-eval*` 與 Ollama 映像。比對寫成函式並有單元測試（用假的清單）。
- 清理：`docker rm -f` 專屬容器、`docker volume rm` 專屬卷（模型在卷內，所以一併清除）；要保留選定的模型時，由命令列的明確旗標與使用者同意才保留卷。
- 不使用也不讀取使用者的 conda 環境與 Hugging Face 快取。

### D8：worker 顯存與共存上限

先用 `read_gpu_memory_mib` 與既有的偵測器載入流程量 worker 在 FP16 的載入後增量（參考既有的紀錄，但**重量一次**，因為驅動與版本可能變）；再量每個模型載入後的整張 GPU 已用量增量與 Ollama 的 `/api/ps` 回報的 `size_vram`，兩者都記。上限約 16 GiB：上限以模型載入後的增量計，加上 worker 增量不得超過整張卡的 32 GiB 並留餘裕；超過者只列為資料。

### D9：候選的查證與確認流程

實作的第一步是**查證，不是拉取**：從 Ollama 目錄與模型卡確認工具呼叫支援、授權、量化後大小與載入顯存估計，產出 3–4 個候選的表格（來源、授權、大小、預估顯存）與預計的下載總量，**停下來等使用者確認**。確認之前專屬卷是空的，Docker 也沒有新增 Ollama 以外的映像。候選表格存在報告草稿中，之後補上實測。

### D10：報告與原始結果

`docs/llm-selection.md`（繁體中文）：方法、門檻（先於結果寫明）、候選表格、每個候選的四項指標與原始結果檔位置、失敗案例與原因、延遲、顯存、worker 增量、結論、限制與沒驗證的事。原始結果（每次試驗的完整紀錄，約 30 題 × 3 次 × 候選數）放 `docs/llm-selection-results/`，小到可以進版控。

## Risks / Trade-offs

- **模型更新很快，名單會過時** → 報告記錄日期、映像與模型的摘要；結論只主張「在這組題目與這個日期的名單內」。
- **結構化輸出掩蓋行為** → 限制段寫明；agent 的 change 會用真實的呼叫流程再驗證。
- **只有一個真實序列** → 題目的類型比序列重要（都是結構化查詢）；報告寫明，不外推到其他場景。
- **工具與標準答案雖獨立，仍可能同時誤解定義**（例如底邊中心點） → 定義寫在 spec 與工具描述中，手算題檢查定義本身。
- **全部候選不達標** → 不降低門檻；回報並讓使用者決定是調整題目、門檻或改走其他做法。
- **拉取量大、佔磁碟** → 確認名單時先告知總量；專屬卷結束後清除；磁碟剩餘 488 GB。
- **顯存餘裕與 worker 的搶用** → 只選可共存者；其餘只當資料。
- **Ollama 版本變化影響行為** → 釘版本並記錄摘要。

## Open Questions

- 具體的候選名單與 Ollama 映像標籤：實作時查證後交由使用者確認（D9），不影響 spec 與任務拆分。
